# 신규 API 추가 표준 절차

이 문서는 Culture Here에 신규 API를 추가할 때마다 재사용하는 운영 기준이다. ChatGPT의 내부 메모리에만 의존하지 않으며, 저장소에 기록해 다음 작업에서도 기준으로 삼는다.

## 사용자 요청 기본 해석

사용자가 신규 API를 등록했다고 말하면, 별도의 재요청 없이 다음 단계 전체를 진행한다. 단, 사용자가 작업 중단을 지시했거나 승인·권한·비용·보안상 확인이 필요한 단계는 예외다.

## 표준 작업 순서

1. **사전 확인**
   - 저장소의 README, `config/apis.json`, `docs/API_REGISTRY.md`, 기존 Collector/Adapter, CI 및 배포 워크플로를 확인한다.
   - 중복 API, 기존 신청·발급 기록, 동일 데이터 제공원을 확인한다.
   - 공식 API 문서와 이용 조건, 인증, endpoint, 파라미터, 데이터 범위, 호출 제한을 조사한다.

2. **API 등록**
   - API Registry에 고유 ID, 이름, 제공기관, 상태, 범위, 인증 방식, Secret 이름, 비활성 상태를 등록한다.
   - Secret 값은 채팅·코드·로그·커밋에 절대 기록하지 않는다.
   - 사용자가 GitHub Secret 등록을 완료했다고 밝힌 경우 이름을 확인하되 Secret의 실제 값은 읽을 수 있다고 주장하지 않는다.

3. **저비용 연결 검증**
   - 최소 요청(가능하면 1건)으로 HTTP 상태, 인증, API 내부 resultCode/resultMsg, 응답 형식, 필드 구조를 검사한다.
   - 성공 응답만으로 전체 데이터 또는 전국 범위를 검증했다고 판단하지 않는다.
   - 인증·쿼터·IP 등록·승인·서버 오류를 구분한다. 쿼터 초과나 반복 실패에는 불필요한 재시도를 하지 않는다.

4. **Collector/Adapter 구현**
   - 기존 공통 데이터 구조를 우선 사용하고 신규 API 전용 Collector/Adapter를 추가한다.
   - 페이지네이션, 요청 제한, 중복 제거, 안정적인 ID, 오류 처리, 재시도 정책, 체크포인트/실패 시 기존 데이터 보호를 구현한다.
   - 원본에 없는 값은 추정해 채우지 않는다.
   - 데이터셋과 실행 로그는 기존 데이터와 분리해 안전하게 테스트한다.

5. **데이터 검증**
   - 수집 건수와 API totalCount 비교
   - 페이지네이션 완료 여부 및 마지막 페이지 확인
   - JSON/필드 구조 검사
   - 필수값 누락·날짜 오류·좌표 오류 검사
   - 중복 레코드와 반복 페이지 fingerprint 검사
   - 지역명/주소 매핑 검사 및 지역 미확인 분리
   - 수집 실패 시 기존 정상 데이터 보존

6. **통합**
   - 검증된 데이터만 공통 스키마로 변환한다.
   - API 간 중복 가능성, 검색·필터·지도·상세 페이지 영향을 점검한다.
   - API별 출처, 원본 링크, 수집 시각을 유지한다.
   - API 활성화는 연결 성공이 아니라 데이터 검증까지 통과한 후 결정한다.

7. **CI 및 배포**
   - 문법 검사와 관련 테스트를 수행한다.
   - 가능한 경우 Collector 실행과 artifact 저장을 분리해 검토한다.
   - 기존 GitHub Actions 및 Pages 배포 체계를 확인하고, 데이터 변경은 검증 성공 후에만 반영한다.
   - 실행/배포 권한이 없으면 사용자가 수행할 단계와 정확한 화면 경로를 안내한다. 실행하지 않은 작업을 완료했다고 말하지 않는다.

8. **오류 자동 복구**
   - 실패 로그와 오류 응답을 분석해 원인을 분류한다.
   - 코드, 파싱, 매핑, 페이지네이션, 설정 등 수정 가능한 오류는 자동 수정 후 문법 검사·테스트·재검증을 시도한다.
   - API 키 발급/교체, 승인, 권한, IP 등록, 쿼터 초기화, 외부 서비스 장애 등 사용자/기관 조치가 필요한 문제는 자동 해결을 시도하지 않고 원인과 필요한 조치를 보고한다.
   - 자동 수정 반복 횟수는 제한하고, 동일 실패에 무한 재시도하지 않는다.

9. **결과 보고**
   - 완료/실패/미검증 상태를 구분한다.
   - API 요청 횟수(확인된 수치만), 응답 코드, 수집/고유/중복 건수, 페이지 수, 검증 항목, 수정 내용, 배포 여부, 남은 문제를 보고한다.
   - 신규 API별 문서와 변경 파일, 커밋 및 Actions 링크를 제공한다.

## 상태 기준

- `candidate`: 조사 후보
- `registered`: Registry 등록, 아직 연결 검증 전
- `connection-verified`: 최소 연결 및 인증 응답 검증
- `collection-verified`: 수집 및 페이지네이션 검증
- `data-validated`: 정규화·품질·중복·지역 검증 통과
- `integrated`: 서비스 공통 구조에 통합
- `deployed`: 배포 및 실제 화면 확인
- `blocked`: 외부/사용자 조치 필요
- `failed`: 테스트 실패; 원인 기록

## 안전 및 운영 제한

- API 테스트는 호출 제한과 쿼터를 우선 고려한다.
- 사용자가 승인하지 않은 신규 유료 서비스, 결제, 데이터 공유, 공개 범위 변경은 진행하지 않는다.
- Secret은 절대 출력하거나 저장소에 기록하지 않는다.
- 기존 정상 데이터는 검증 실패 시 덮어쓰지 않는다.
- README, Registry, 이 절차 문서를 갱신해 운영 기록을 남긴다.
- 작업이 중단/보류되면 마지막 검증 지점, 미완료 항목, 다음 실행 단계가 재개 가능하도록 기록한다.
